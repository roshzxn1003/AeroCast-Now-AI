# AeroCast-Now AI: Model Lifecycle & Monitoring Audit (Phase 10 - Step 1)

## 1. Executive Summary
This audit provides a comprehensive evaluation of the existing machine learning lifecycle, prediction tracking, verification systems, and monitoring infrastructure in **AeroCast-Now AI** as built through Phase 8 and Phase 9. It establishes the baseline for implementing Phase 10: Model Monitoring, Continuous Validation & Controlled Retraining.

---

## 2. Current Model Loading & Management
- **Primary Loader**: [`backend/ml/model_manager.py`](file:///home/arun-roshan-gj/SIH/backend/ml/model_manager.py) manages a thread-safe singleton `ModelManager`.
- **Warmup Execution**: At application boot, `_boot_live_feeds` triggers `get_model_manager()`, running an initial dummy tensor pass through TensorFlow to compile computation graphs and stabilize latency (down to ~12ms).
- **Model Registry (Phase 8 baseline)**: [`backend/ml/model_registry.py`](file:///home/arun-roshan-gj/SIH/backend/ml/model_registry.py) syncs `.keras` files into the `model_registry` table in SQLite (`convlstm_real_best` as PRODUCTION, `convlstm_nowcaster` as STAGING, `weather_lstm` as STAGING).
- **Integrity Check**: SHA-256 hash is computed on disk files, but currently lacks runtime enforcement that blocks loading if an artifact changes unexpectedly.

## 3. Current Prediction Generation & Recording
- **Forward Inference**: Predictions are generated by `ModelManager.predict_frames(tensor)` where `tensor` has shape `(1, 4, 32, 32, 4)`.
- **Pre-inference Gate (Phase 9)**: `InferenceReadinessGate` in [`backend/ingestion/inference_gate.py`](file:///home/arun-roshan-gj/SIH/backend/ingestion/inference_gate.py) verifies numerical validity, temporal completeness, and provider health before permitting model handoff (`READY`, `DEGRADED`, `BLOCKED`).
- **Prediction Identification**: Predictions receive a unique ID `PRED-<uuid12>` via [`backend/core/prediction_record.py`](file:///home/arun-roshan-gj/SIH/backend/core/prediction_record.py).
- **Persistence**: Prediction records are written to the `predictions` table in SQLite (`data/aerocast.sqlite3`), including:
  - `model_id`, `model_version`, `model_hash`
  - `station`, `generated_at`, `valid_time`, `lead_time_min`
  - `max_dbz`, `max_vil`, `has_jump`, `storm_count`
  - JSON inputs: `input_timestamps_json`, `data_sources_json`, `prediction_payload_json`
  - `verified`: Boolean flag initialized to 0.

## 4. Current Forecast Verification Process
- **Engine**: [`backend/verification/verification_engine.py`](file:///home/arun-roshan-gj/SIH/backend/verification/verification_engine.py) queries unverified records where `valid_time <= now_utc`.
- **Matching**: Matches mature predictions against observed truth (`observed_max_dbz`, storm centroids).
- **Metrics Calculated**:
  - Continuous error: `dbz_error = predicted_max_dbz - observed_max_dbz`
  - Categorical contingency: Hit, Miss, False Alarm, Correct Negative at threshold (default 35 dBZ)
  - Location error: Haversine distance in km between predicted and observed storm centroids
- **Weaknesses in Current Matching**:
  - Verification currently only evaluates a single scalar maximum dBZ and storm centroid per prediction, rather than full multi-horizon 2D grid fields (+15m, +30m, +45m, +60m).
  - Missing observation handling does not explicitly flag `VERIFICATION_STATUS = UNAVAILABLE`; it simply fails to verify.
  - Baselines (Persistence, Climatology) are not automatically computed alongside model forecasts.

## 5. Current Training & Dataset Split Pipeline
- **Script**: [`backend/train_nowcasting_model.py`](file:///home/arun-roshan-gj/SIH/backend/train_nowcasting_model.py)
- **Splits**: Implements chronological train/val/test splits to avoid temporal leakage.
- **Loss**: Weighted Balanced Meteorological Convective Loss (BMAE) prioritizing severe convective cores ($\ge 35\text{ dBZ}$, $\ge 25\text{ kg/m}^2$, $\ge 10\text{ flashes/km}^2$).
- **Weaknesses in Current Training**:
  - Training metrics in historical documentation stem largely from synthetic/development simulations. These must be segregated from real-world empirical validation.
  - Retraining workflow is manual via CLI arguments rather than an auditable request-and-review lifecycle.
  - No automated drift detection or performance decay alerts triggering retraining requests.

## 6. Target Architecture for Phase 10
To fulfill Phase 10 requirements, the following systems will be constructed:
1. **Model Identity & Checksum Verification**: Enforce artifact integrity on load with operational error halting.
2. **Multi-Horizon Continuous Verification Pipeline**: Automated background matching across $+15, +30, +45, +60, +90, +120\text{m}$ horizons, storing continuous (MAE, RMSE, Bias, Correlation), categorical (POD, FAR, CSI, HSS, ETS, F1), and probabilistic metrics.
3. **Operational Baselines**: Comparative verification against Persistence and Climatology.
4. **Event-Based Storm Verification**: Storm event clustering, location error, detection lead time, and false alarm cause analysis.
5. **Data & Performance Drift Engine**: Population Stability Index (PSI), KS test, and moving-window degradation tracking across radar, satellite, lightning, and sounding channels.
6. **Controlled Retraining Lifecycle**: Retraining requests, chronological holdout evaluation, shadow testing, human review gates, and instant rollback mechanism.
7. **Operational Monitoring APIs & Frontend Dashboards**: Complete visibility into model health, drift, and verification.
